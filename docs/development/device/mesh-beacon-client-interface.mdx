:::warning
The Mesh Beacon Module is under active development. Its settings and behaviour can still change between releases, so treat this page as a description of current firmware rather than a settled interface.
:::

**Firmware 2.8.0 or later** ([#10618](https://github.com/meshtastic/firmware/pull/10618)). Detect support at runtime as described under [Capability detection](#capability-detection) rather than by version number - the module is also build-flag optional, so a 2.8.0 device may still not carry it.

This page is the client-side specification for the Mesh Beacon module. Everything goes through the **standard admin, ToRadio and FromRadio protocol** - there is no bespoke transport. For what the module does and how it is configured from a user's point of view, see [Mesh Beacon Module Usage](/docs/configuration/module/mesh-beacon).

## The wire message

Beacons travel on their own port number, `MESH_BEACON_APP = 37`, with a protobuf payload:

```protobuf
message MeshBeacon {
  string message                            = 1;  // human-readable text, max 60 bytes
  ChannelSettings offer_channel             = 2;  // optional advertised channel
  Config.LoRaConfig.RegionCode offer_region = 3;  // optional advertised region (UNSET = none)
  optional Config.LoRaConfig.ModemPreset offer_preset = 4; // optional advertised preset
  optional uint32 offer_frequency_slot      = 5;  // 1-based; omitted when derivable
}
```

Size caps are enforced both at generation and on send: `message` up to 60 bytes, `offer_channel.name` up to 12, `offer_channel.psk` up to 32.

Every outgoing beacon is stamped uniformly: broadcast destination, `from` the local node, `hop_limit = 0`, background priority, and no ACK request.

### offer_channel

A broadcaster fills in only `name`, `psk` and `use_aead`. The other `ChannelSettings` fields - `id`, `uplink_enabled`, `downlink_enabled`, `module_settings` - describe the advertising node's own posture, are never meaningful to a receiver, and are sent zeroed. An empty `name` means the modem preset's display name. A cleartext channel is sent as the one-byte `psk` `0`, never as an empty `psk`: a receiver adding an empty PSK as a secondary would inherit its own primary's key.

### offer_frequency_slot

Present only when a receiver **could not work the slot out for itself**. Derive it as any node on that channel would: the offered region's override slot if it has one, otherwise the hash of `offer_channel.name`, evaluated for the bandwidth that `offer_region` and `offer_preset` imply. An unset `offer_preset` means the region's default preset.

When the field is present, the advertising mesh deliberately sits somewhere other than derivation would put it, so use the value given. Either way, **validate the result against the user's own region before offering to join** - a slot number is only meaningful together with a region and a bandwidth. A `0` is never sent; treat it as absent.

## Capability detection

The module is build-flag optional. Treat it as present when the node's `LocalModuleConfig` contains a `mesh_beacon` sub-message. If it is absent, the firmware was built without the module - hide the beacon UI.

## Reading and writing configuration

Standard module-config flow; there are no new admin messages.

- **Read:** `AdminMessage.get_module_config_request` for the mesh beacon variant. The reply is `get_module_config_response` carrying the `mesh_beacon` payload.
- **Write:** `AdminMessage.set_module_config { mesh_beacon = … }`.

The on/off toggles are bits in the `flags` field, not separate booleans: `FLAG_LISTEN_ENABLED = 1`, `FLAG_BROADCAST_ENABLED = 2`, `FLAG_LEGACY_SPLIT = 4`. To toggle one bit, read the current `flags`, set or clear the bit, and write the whole config back.

Setting beacon config does **not** trigger a reboot; changes take effect on the next broadcast cycle.

### Size limit on remote writes

A beacon config written **over the mesh** must fit one PKC-encrypted LoRa frame: at most **214 bytes** for the encoded `AdminMessage`, session passkey included (255, less the 16-byte header, 12 bytes of PKC overhead and 13 of `Data` framing). A write that does not fit is refused with `Routing.Error TOO_LARGE` and nothing is stored, including any channel it would have created.

The bound exists because the read-back would truncate to an empty payload, which the sending client sees as a silent success. Refusing is the only outcome that tells the truth.

The largest configuration the schema allows encodes to 181 bytes: four targets each with region, preset, channel index and slot, an offer with an 11-character name, a 32-byte PSK, region, preset and slot, and a 60-byte message. Every valid config fits. The same config written from a locally connected client is always accepted; over 214 bytes the client is warned that no remote administrator could read it back.

### Sanitisation rules to mirror client-side

The firmware adjusts values on write, so your value may be silently changed. After a successful write, **re-read** the config and display the effective values.

| Rule | Firmware behaviour |
| :--- | :----------------- |
| `broadcast_message` length | Truncated to 60 bytes, never mid-character. |
| `broadcast_interval_secs` | If non-zero and below 3600, raised to 3600. |
| `broadcast_offer_region` not a known region | Cleared to `UNSET`, which means "use the running region". |
| `broadcast_offer_preset` not a valid preset value | Cleared. A preset the region cannot run is **kept** - it describes a mesh elsewhere. |
| `*_frequency_slot` of `0` | Cleared. `0` is the encoding of "unset". |
| `*_frequency_slot` out of range, **with** an explicit region and preset | Cleared. That pair fixes the bandwidth, so the slot count cannot move later. |
| `*_frequency_slot` out of range, without both | **Kept.** The bound would be the running radio's, and a later region change would silently delete a deliberate pin. |
| `broadcast_targets[i].region` not a known region | That entry's region cleared to `UNSET`; transmission falls back to the running config. |
| `broadcast_targets[i].preset` not a valid preset value | That entry's preset cleared. As above, an unrunnable preset is kept. |
| `broadcast_offer_channel.psk` empty | Stored and advertised as the one-byte `0` key, which means no encryption. |
| `broadcast_offer_channel` is not in the channel table | Added to it. If it cannot be placed, the offer is kept and withheld - see [The offer channel is written to the channel table](#the-offer-channel-is-written-to-the-channel-table). |
| A channel a target or the offer uses is disabled afterwards | Nothing is removed. Targets naming that slot are skipped at send and the offer is withheld while its channel is not live; the client is told what was withheld. |

## Receiving beacons

A received beacon reaches the client as a normal `FromRadio.packet` - the listener does not consume it on-device. To handle beacons:

1. Subscribe to the FromRadio packet stream as usual.
2. For packets whose `decoded.portnum` is `MESH_BEACON_APP (37)`, decode `decoded.payload` as a `MeshBeacon`.
3. Read `message`, `offer_channel`, `offer_region`, `offer_preset` and `offer_frequency_slot`, presence-checked.
4. `packet.from` is the **originating beaconer**; the firmware preserves it.

:::warning
This requires `FLAG_LISTEN_ENABLED`. With listening disabled the firmware drops received beacon packets in the router - before they reach the phone or any on-device handler - so the client will not see beacons at all, even though the node is physically receiving the RF.
:::

### Reading the text, without duplication

For a beacon-aware client the text is **the `message` field of the beacon packet** you already decode for the offer. One packet, one field: the firmware does not inject a separate text-message copy, so there is nothing to deduplicate.

Splitting happens only when a beacon has **both** text and offer content and the broadcaster set `FLAG_LEGACY_SPLIT`. In that one case the broadcaster emits two packets on the same radio settings: a `MESH_BEACON_APP` packet carrying the offer with an empty message, and an ordinary `TEXT_MESSAGE_APP` packet carrying the text, so that non-beacon-aware clients can still display it.

What the broadcaster emits, in full:

| Beacon content   | `FLAG_LEGACY_SPLIT` | Packets sent                                              |
| :--------------- | :------------------ | :-------------------------------------------------------- |
| Offer + text     | Not set             | One `MESH_BEACON_APP` carrying both offer and `message`   |
| Offer + text     | Set                 | Two: `MESH_BEACON_APP` (offer only) + `TEXT_MESSAGE_APP`  |
| Offer only       | Either              | One `MESH_BEACON_APP`, `message` empty                    |
| Text only        | Either              | One `TEXT_MESSAGE_APP` - no beacon packet at all          |

Two consequences for a client. First, a given beacon's text always appears exactly once, so there is never anything to deduplicate - render whichever form arrives. Second, a text-only beacon is indistinguishable from an ordinary text message on the wire: the broadcaster sends no `MESH_BEACON_APP` packet, so there is no `MeshBeacon.message` to read and no beacon for the client to attribute it to.

Note that a legacy-split beacon is stamped `hop_start = 1` with `hop_limit = 0`, so it computes as 1 hop away despite arriving over direct RF. Do not treat a beacon's hop distance as a proximity signal.

## Acting on an offer

This is the core client responsibility. When a beacon carries offer content, present it as an **invitation** - for example *"Node ⟨from⟩ invites you to join '⟨offer_channel.name⟩' on ⟨preset⟩/⟨region⟩."* Then, only on explicit user confirmation, apply it by writing normal config:

- `offer_channel` becomes an added or replaced `Channel` via `set_channel`, typically as a secondary channel.
- `offer_region` and `offer_preset` become a `set_config { lora = … }` write with `use_preset` on.
- `offer_frequency_slot`, or the slot you derived, becomes `lora.channel_num` in that same write.

:::danger
Applying an offered region or preset **changes the node's own radio and will drop it off its current mesh.** Make that consequence explicit in the UI before the user confirms.
:::

**The firmware will never do any of this for the user, and there is no silent auto-apply.** The on-device offer cache is a firmware-internal convenience and is not exposed over an admin message - source offers from the live packet stream rather than expecting a "get last offer" call. Note also that the cached timestamp is `0` when the node has no clock fix yet; never treat `0` as a valid time.

### Offer trust model

- **The advertised PSK is not a secret.** It is a public join token sent in the clear inside a broadcast - a convenience, not a security boundary. Surface offered channels to the user as public or open.
- **Validate before applying.** Reject or warn when the offered preset is not valid for the offered region, when the frequency slot falls outside that region, and **never** apply a licensed-only (amateur) region for a user who is not a licensed operator. Mirror the firmware's own guard.
- **Treat `from` as informational.** A beacon asserts nothing about the sender's authority.

## Configuring a node as a broadcaster

Write the config with `FLAG_BROADCAST_ENABLED` set and at least one of a non-empty `broadcast_message` or some offer content. With neither, the broadcaster has nothing to send and stays silent.

### How channels are named

| | Offer (`broadcast_offer_channel`) | Targets (`broadcast_targets[i].channel_index`) |
| :--- | :--- | :--- |
| Named | by value: name, PSK, `use_aead` | by index into the node's channel table |
| Channel must already exist | no, the write places it | yes |
| Unset | no offer | the beacon goes out on the primary channel, retuned to the target's preset, region and slot |

The offer is by value because it is the advertisement payload and must carry the real name and PSK. Targets are by index because the node needs a key it already holds to encrypt.

A **remote administrator** must read the node's channel table before writing targets: send `AdminMessage.get_channel_request` for each slot (the request value is the index plus one, `1..8`) and pick the index from the replies. An index written without reading resolves to whatever that slot holds, which may be a different channel, or a disabled slot that is skipped at send. A target left without an index needs no read.

### The offer channel is written to the channel table

`broadcast_offer_channel` is **upserted** into the node's channel table when the config is written, so the node holds the channel it advertises. The rules:

1. A live channel with the same name, PSK and `use_aead` is reused; nothing is written.
2. Otherwise the lowest disabled slot is claimed as a `SECONDARY`, preferring one that previously held this same identity, so re-adding a deleted channel gets its old index back.
3. A live channel is **never** overwritten, and the primary is never displaced.

If no slot can be claimed, or a licensed node is offered an encrypted channel, the offer is **kept in the config and withheld** from the air, and the client is warned. It is advertised again once its channel can be placed. The message text still goes out.

A write that places the channel saves the channel table as well as the module config. For a write from a **locally connected** client, the node then sends that client an unsolicited `AdminMessage.get_channel_response` for the claimed slot, with `from` set to the node's own number, because channels otherwise reach a client only in the connect-time config dump. A write from a remote administrator sends nothing; re-read the channel table to see where the channel landed.

### Indexed targets take two writes, in order

1. **Create each channel** in the node's channel table with the normal channel admin flow:

   ```text
   AdminMessage.set_channel { index: 1, role: SECONDARY,
                              settings: { name: "NarrowSlow", psk: <key> } }
   ```

2. **Write the beacon config**, pointing each target at the slot from step 1:

   ```text
   AdminMessage.set_module_config { mesh_beacon: {
       flags = FLAG_BROADCAST_ENABLED
       broadcast_targets = [ { preset: NARROW_SLOW, region: EU_N_868, channel_index: 1 } ]
   } }
   ```

Over the mesh, read the channel table between the two steps to confirm the index.

### Validating channel references is the client's job

A target may only reference a channel that already exists locally, because the node needs that channel's key to encrypt the beacon. A `channel_index` that is out of range, or points at a disabled slot, is **not** a write error and is stored as written, because a client may legitimately write the beacon config before creating the channel.

At transmit time such a target is **skipped**: no beacon is sent for it, and it is not redirected onto another channel. The entry stays in the config, so provisioning the channel later brings the target back without a rewrite. Disabling a channel that a target names keeps the target and skips it in the same way.

Before writing, confirm each index maps to a configured channel and warn otherwise, or the user will believe they are advertising a mesh that is never actually broadcast to.

There is also **no automatic deduplication of channels**: two targets may carry the same index, or different indices whose slots hold identical settings, and `set_channel` will happily store two slots with the same name and PSK. The broadcaster skips transmitting a target whose effective settings duplicate an earlier one in the same cycle, so a duplicate wastes no airtime, but it does not rewrite or reject the config. Keeping the target list free of redundant entries is up to the client.

## Quick reference

| Concern                | Value                                                                                    |
| :--------------------- | :--------------------------------------------------------------------------------------- |
| Port number            | `MESH_BEACON_APP = 37`                                                                   |
| Wire message           | `meshtastic.MeshBeacon`                                                                  |
| Config message         | `ModuleConfig.MeshBeaconConfig`                                                          |
| On/off toggles         | `flags` bitfield (`MeshBeaconConfig.Flags`)                                              |
| Local config presence  | `LocalModuleConfig.mesh_beacon`                                                          |
| Min broadcast interval | 3600 s (1 h)                                                                             |
| Message max length     | 60 bytes                                                                                 |
| Channel name / PSK max | 12 bytes / 32 bytes                                                                      |
| Remote write ceiling   | 214 bytes encoded `AdminMessage`, else `Routing.Error TOO_LARGE`                         |
| Frequency slots        | 1-based, matching `Config.LoRaConfig.channel_num`; `0` means unset                       |
| Hop behaviour          | Zero-hop (`hop_limit = 0`), never rebroadcast; `hop_start = 1` under legacy split         |
| Auto-apply offers?     | **Never** - the client and user decide                                                   |
| Offer PSK              | Public join token, not a secret                                                          |
